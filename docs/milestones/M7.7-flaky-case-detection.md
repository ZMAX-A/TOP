# M7.7：Flaky Case 识别

## 目标与完成范围

M7.7 在 M7.6 的统一质量筛选边界上识别重复出现、结果来回变化的 Case，避免把一次性回归、已修复问题或
执行基础设施故障误报为 Flaky。本阶段完成：

- 质量分析响应增加 `flaky` 分析结果，并继续复用窗口、目标、环境和 Released 基线筛选；
- 只分析 `PASSED` 和 `FAILED` Case 结果，`TIMED_OUT`、`INFRA_ERROR`、`CANCELED` 与 `SKIPPED`
  不参与产品稳定性判定；
- 同一 `case_id` 至少有 3 次有结论执行，并按 Run 完成时间排序后发生至少 2 次
  `PASSED/FAILED` 状态切换，才标记为 Flaky；
- 每条结果公开通过/失败次数、通过率、状态切换次数、切换率、最新状态和最新完成时间，判定过程可审计；
- Vue 质量分析页展示 Flaky Case 表格、检测规则、分析样本数和截断状态；
- 一次性的 `PASSED -> FAILED` 或 `FAILED -> PASSED` 只代表可能的回归或修复，不归入 Flaky。

## 数据与排序语义

Case 历史按 `coalesce(run.finished_at, run.updated_at)` 的 UTC 时间升序排列；相同时间使用 Run ID 稳定排序。
跨基线分析时使用稳定 `case_id` 聚合并展示最近一次记录的 `case_code`。结果按切换率、切换次数、样本数和
最近发生时间排序，最多返回前 20 个 Case。

## 安全与性能边界

- Flaky 查询继续要求项目 `run:read` 权限，维度 UUID 不扩大项目边界；
- 最多读取当前筛选范围内最近 5000 条有结论 Case 结果；超过上限时 `data_truncated=true`，调用方不得把
  检测数量解释为完整总量；
- 当前直接读取 `test_runs` 与 `run_cases` 事实表，复用 Run ID 和质量维度索引，不新增派生状态表或迁移；
- 固定规则优先保证可解释性。只有在真实 PostgreSQL 数据证明需要后，才引入可配置阈值或物化聚合。
