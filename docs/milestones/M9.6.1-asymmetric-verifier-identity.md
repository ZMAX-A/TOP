# M9.6.1 工作负载身份与 Ed25519 验证器 Envelope

## 目标

M9.4.2 的短时 HMAC Envelope 已覆盖方法、路径、请求体摘要、签发时间和 nonce，但 API 与验证器仍共享秘密，密钥泄漏
会同时扩大签名和验证边界。M9.6.1 将默认认证切换为 Ed25519 detached JWS：验证器工作负载独占私钥，控制面只配置
公钥、credential id 和批准的 HTTPS/SPIFFE 工作负载身份。M9.4.2 的历史 Envelope 保持可读，旧 HMAC 请求默认关闭。

## Ed25519 Envelope Profile

`testops-supply-chain-envelope-v2` 的 UTF-8 payload 依次包含：profile、HTTP 方法、请求路径、Unix created、小写 UUID
nonce、原始请求体 SHA-256、credential id 和绑定的工作负载身份。JWS protected header 只允许：

- `alg=EdDSA`；
- `kid=<verifier>/<key-id>`，且必须与 `X-TestOps-Verifier-Key-Id` 完全一致；
- `typ=testops-supply-chain-envelope+jws`。

请求通过 `X-TestOps-Envelope-Signature: <protected>..<signature>` 传递 compact detached JWS。实现拒绝内嵌 payload、额外
Header、非规范 base64url、非 64 字节签名、未知/已移除 key、身份替换、错误签名、过期和未来超限时间。nonce 继续由
`(credential_id, nonce)` 数据库唯一约束提供跨进程并发防重放。

Ed25519 验证采用 PyCA cryptography 的 `Ed25519PublicKey.from_public_bytes(...).verify(...)`，不在平台代码中实现密码算法。
官方接口会在签名无效时失败，公钥必须是 32 字节原始编码。

## 公钥环、身份与轮换

`SUPPLY_CHAIN_VERIFIER_ED25519_KEYS` 使用 JSON 数组，每项只允许：

```json
{
  "credential_id": "ci-cosign-slsa-verifier/2026-08-ed25519",
  "workload_identity": "https://github.com/example/testops/.github/workflows/release.yml",
  "public_key": "<32-byte-raw-key-as-unpadded-base64url>"
}
```

控制面最多接受 16 个不重复 credential 和公钥指纹。相同工作负载身份可以在轮换窗口同时绑定旧、新公钥；审计 actor
由工作负载身份稳定派生，因此换 key-id 不改变机器主体。Envelope 新增 profile、签名算法、工作负载身份和公钥 SHA-256
指纹，工作台可直接区分旧 HMAC 与 Ed25519 证据。

轮换顺序是：生成新私钥 → 同时配置新公钥 → 重启 API → 验证器切换新 key-id → 观察新 Envelope 与指纹 → 移除旧公钥。
私钥不进入 API、数据库、前端、Worker、Compose 公共环境或审计。HMAC 只有在
`SUPPLY_CHAIN_ALLOW_LEGACY_HMAC=true` 时才接受；默认 false，迁移完成后必须移除共享秘密。

## 数据库与兼容

迁移 `20260821_0019` 为 Envelope 表增加 profile、算法、工作负载身份和公钥指纹。已有行回填 v1/HMAC-SHA256，身份与
公钥指纹保持空；新 Ed25519 行必须使用 v2 且身份、指纹均非空，数据库检查约束阻止混合证据。降级到 `0018` 只删除
新增列，不改写供应链验证记录、包状态或 Run Snapshot。

## 验证边界

本阶段覆盖公钥配置解析、身份 URI、重复 credential/公钥、双 key 轮换、错误密钥、身份替换、未知 key、时间窗、nonce
重放、业务幂等、Envelope 查询、数据库约束、迁移图、前端证据展示和部署变量隔离。生产仍需使用真实工作负载生成的
随机私钥，在 TLS 入口完成旧/新 key 并存、切换、撤销和审计演练。

本阶段是固定公钥到工作负载身份的第一步，不等同于 OIDC/SPIFFE 联邦验证。后续可接入发行方信任根和短期工作负载
凭证，避免静态公钥分发；执行侧继续推进短期 Registry/对象存储凭据、项目级网络策略编译和沙箱指标。

## RC1 可信验证器客户端

RC1 增加 `scripts/submit_supply_chain_verification.py`，把测试中已验证的 v2 字节级协议提取到共享 contracts，供 API
验签与 CI 签名共同使用。客户端在发送前验证报告契约、credential/verifier、HTTPS/SPIFFE 身份、canonical created 和
nonce；默认只允许 HTTPS origin、拒绝重定向，私钥只从有界文件读取，输出不包含私钥或签名 Header。生产 CI 仍需自行
执行真实 Cosign、透明日志、SLSA provenance、SBOM 和漏洞策略，并把其结果写入提交报告。
