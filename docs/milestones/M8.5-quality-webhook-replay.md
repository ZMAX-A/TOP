# M8.5 质量 Webhook 失败投递人工重放

## 目标

为 M8.2–M8.4 的持久化质量通知链路补齐受控的失败恢复入口：项目管理员在确认接收端、网络或签名配置已修复后，
可以对明确进入 FAILED 的投递执行一次可追溯重放，同时保留原失败证据并避免并发或重复操作制造多份通知。

## 已实现

- `POST /api/v1/projects/{project_id}/quality/webhook/deliveries/{delivery_id}/replay` 只接受项目内 FAILED 投递，
  要求 `project:manage`、已启用的 Webhook 配置和最多 500 字的非空重放原因；
- 重放创建新的 PENDING 投递而不修改原记录；新记录保存直接来源、操作者和原因，使用当前配置的目标与签名密钥，
  但复制原始事件载荷并保留 `event_id`，便于接收端继续执行事件级幂等；
- 每个失败节点通过数据库唯一约束最多生成一个直接重放子记录。若子记录再次失败，管理员应从该新失败节点继续，
  从而形成线性、可审计的尝试链；
- 非失败、跨项目、重复重放以及禁用配置均失败关闭；操作审计只记录脱敏目标、状态码、尝试次数和原因，不保存
  真实 URL 路径、响应正文或密钥引用；
- 最近投递 API 返回重放来源和操作元数据；Vue 质量分析页只为项目管理员显示 FAILED 行的重放入口，并展示来源、
  原因和“已重放”状态；
- Alembic `20260817_0015` 增加自引用来源、操作者、原因、全空/全非空检查和单来源唯一约束，平台版本提升到
  `0.20.0`。

## 事务与幂等边界

- 服务先锁定项目和来源投递，再检查既有子记录与当前配置；PostgreSQL 行锁配合 `replay_of_id` 唯一约束封闭并发
  双击窗口，dispatcher 仍只消费普通 PENDING 记录；
- 投递记录 ID 表示一次具体发送，载荷 `event_id` 表示业务事件。人工重放生成新的投递 ID、沿用业务事件 ID，既
  保留平台尝试历史，也允许接收端避免“已处理但响应丢失”导致的重复副作用；
- 重放不绕过 SSRF、HTTPS 443、签名密钥、有界重试或响应正文不落库等既有安全边界，也不改变质量告警状态机、
  冷却期、确认或静默状态。
