# M9.3 自动化包生命周期工作台

## 目标

把 M9.1 的自动化包生命周期 API 和 M9.2 的精确运行时准入变成项目管理员可直接操作的发布工作流。脚本更新后，
管理员不再需要拼接 API 请求或手工保存验证 Run ID，而是在同一项目页面完成新版本草稿、全量验证、激活、弃用
和安全吊销，并能从包版本反查关联执行记录。

## 已实现

- 新增项目级“自动化包”工作台与项目首页入口，按 Web 目标隔离展示包版本总数、草稿、已激活和已吊销数量；
- 版本目录展示 `name@version`、生命周期状态、Runner 类型、OCI 仓库、完整不可变摘要、替代关系、激活证据和状态
  变更原因；列表只显示摘要缩写，详情保留完整值供发布核验；
- Project Admin 和 System Admin 可以创建 DRAFT。表单在客户端先校验小写包名和完整 `sha256`，服务端继续拒绝
  协议、内联摘要、空白与可变标签，替代关系只能选择当前目标内未吊销版本；
- 草稿可选择 ACTIVE 环境与 Released 基线发起全量验证，客户端为每次操作生成独立 Idempotency-Key；关联 Run
  列表直接展示状态、用例数并跳转到执行详情；
- 激活对话框只提供 `PASSED` 且已有不可变 Result 摘要的关联 Run，控制面仍负责校验包归属、Released 基线和全部
  启用用例覆盖，前端条件不是安全边界；
- ACTIVE 版本可带原因弃用，仍被 ACTIVE 回归计划引用时由控制面拒绝；未吊销版本可因安全或完整性事件直接吊销，
  页面明确说明吊销阻止新执行和历史重跑，但不篡改已经在途的 Run；
- Viewer、Tester 和 Reviewer 保留只读目录及关联 Run 能力；生命周期按钮只对 Project Admin/System Admin 显示，
  所有写操作仍由服务端 `project:manage` 权限和审计日志保护；
- 项目 Run 列表新增通用 `automation_package_id` 精确过滤条件，保持原有分页、项目授权和倒序语义，可供工作台和
  后续包级质量分析复用。

## 脚本更新后的界面操作

1. CI 构建、测试和扫描新的 Worker/Runner 镜像，取得最终 OCI Manifest Digest；
2. 先滚动部署能同时声明旧、新摘要的 Worker，在系统管理中心确认新不可变引用与可用槽位；
3. 进入项目首页的“自动化包”，选择 Web 目标和待替代版本，创建新版本 DRAFT；
4. 对 DRAFT 发起 Released 基线全量验证；若 Run 等待原因为 `AUTOMATION_PACKAGE_UNAVAILABLE`，修复 Worker 部署，
   不修改 Snapshot，也不把摘要替换成可变标签；
5. 验证 Run 进入 PASSED 后，在同一页面选择该 Run 激活新版本；再把普通执行和回归计划逐步切换到新版本；
6. 暂停或迁移仍引用旧版本的 ACTIVE 回归计划，然后填写原因弃用旧版本；遇到供应链风险时跳过弃用，直接吊销；
7. 保留仍需历史重跑的旧运行时容量；确认不再需要后，才从 Worker 目录移除旧摘要。

## 兼容与版本

- 平台版本提升到 `0.24.0`，Alembic Head 继续为 `20260820_0016`；本切片不新增表或迁移；
- `GET /api/v1/projects/{project_id}/runs` 新增可选 `automation_package_id`，未提供时响应与之前完全一致；
- 现有 M9.1 生命周期端点、M9.2 Worker 目录、Run Snapshot、Result 和审计记录均不改变；
- 工作台当前只承载 `WEB_PLAYWRIGHT`，APP/API 目标等对应 Runner 契约落地后再扩展，不能用 Web 表单伪造不受支持
  的运行类型。

- 全量 Pytest `100 passed`，仓库依赖精简入口 `75 tests OK`；Ruff 检查通过，146 个 Python 文件格式一致；
- 自动化包生命周期集成测试覆盖按包查询关联 Run，并继续覆盖草稿重复约束、幂等验证、过早激活、全量通过激活、
  ACTIVE 回归计划阻断弃用、弃用后禁止新执行、吊销及完整审计动作；
- Vue 严格 TypeScript 检查覆盖新路由、权限分支、表单和 Run 跳转；`0.24.0` 生产构建通过，新工作台被 Vite 正确
  生成独立页面分包；
- 发布元数据检查要求 `0.24.0` 在 Python、API、Worker、Compose、Smoke 与前端包中保持一致，并要求本里程碑文档
  存在；

## 完成边界与后续

M9.3 完成“预装不可变运行时”模式下的人机发布闭环，但不扩大 M9.2 的执行信任边界。远端 Registry 认证与拉取、
OCI 签名和 provenance、SBOM/漏洞策略、每个 Run 独立容器或 Pod、资源限制和网络策略仍未实现；下一阶段应优先建设
签名验证与部署准入，再以不暴露宿主 Docker Socket 的隔离执行器承载动态运行时。
