# M7.4：运行可靠性与队列可观测性

## 目标与完成范围

M7.4 为既有项目配额、Runner Pool 和定时回归链路增加自动收敛能力，避免 Worker 异常退出或任务未被认领后
长期占用在途配额与执行槽位。本阶段完成：

- 项目执行策略新增 `run_timeout_seconds`（60～86400 秒），创建 Run 时将当前值冻结到 Run，后续修改项目
  策略不会追溯改变已创建任务；
- Run 进入 `PREPARING` 时计算 UTC `timeout_at`，运行详情显示冻结上限和明确的 UTC 截止时刻；
- Runner 状态回调可携带 `worker_key`，将 Pool 槽位租约绑定到实际执行 Worker，同时刷新其活动时间；
- 独立 Reaper 通过数据库行锁批量处理执行超时、Worker 心跳过期、已派发但无人认领以及终态残留租约；
- 自动恢复分别将 Run 收敛为 `TIMED_OUT` 或 `INFRA_ERROR`，释放租约、设置取消标记、投递取消 Outbox，
  并写入 Run Event、变更验证状态和审计日志；
- `/metrics` 增加在途 Run、派发等待量与最老等待时长、到期待调度量与计划延迟、失联 Worker 租约等
  低基数指标；
- Prometheus 增加可靠性快照失败、派发积压、定时计划延迟和失联 Worker 租约告警；
- Compose 增加独立 `reaper` 服务，平台版本统一为 `0.12.0`。

## 数据与并发边界

Alembic `20260813_0008` 新增：

- `projects.run_timeout_seconds`；
- `test_runs.timeout_seconds` 与索引化的 `timeout_at`；
- `runner_slot_leases.worker_id` 及到 `runner_workers` 的可空外键。

Reaper 使用 `FOR UPDATE SKIP LOCKED` 选择候选记录，多实例可并行处理不同批次。Run 状态机与终态检查提供第一层
幂等保护，事件和 Outbox 的稳定去重键提供第二层保护，数据库唯一约束负责并发兜底。终态之后到达的迟发 Runner
状态或 Result 会被现有状态机拒绝，不能覆盖自动恢复结论。

## 回收语义

1. `PREPARING` 或 `RUNNING` 达到冻结的 `timeout_at`：转为 `TIMED_OUT`；
2. 已绑定 Worker 的活动租约超过心跳 TTL：转为 `INFRA_ERROR`；
3. 已派发的 `QUEUED` Run 在启动窗口内没有 Worker 认领：转为 `INFRA_ERROR`；
4. 终态 Run 仍存在活动租约：只释放租约，不改变既有结果。

Reaper 可单次运行或持续轮询：

```powershell
python scripts/reap_run_reliability.py
python scripts/reap_run_reliability.py --watch --interval-seconds 15 --batch-size 100
```

Compose 使用 `RUN_REAPER_POLL_SECONDS`、`RUN_REAPER_BATCH_SIZE` 和
`RUN_DISPATCH_START_TIMEOUT_SECONDS` 调整行为。Worker 心跳 TTL 继续由
`RUNNER_HEARTBEAT_TTL_SECONDS` 统一控制。

## 验证门禁与剩余风险

策略冻结、Worker 绑定、三类自动恢复、审计/事件/Outbox、可靠性指标、告警 YAML、Alembic 单 Head 与离线
SQL，以及全量 Python、Vue 和制品门禁均已通过。2026-08-14 的完整 Compose 验收覆盖独立 Reaper 启动、
Redis/Celery 投递、Outbox/Worker 停止后恢复，以及成功和预期失败 Run 的终态与制品闭环。

真实 PostgreSQL 多 Reaper 竞争和 Worker 在执行中异常退出后的端到端回收仍需专项压力/故障注入验收。项目质量
趋势、失败聚类和通过率/SLO 已在 M7.5 实现；容量预测继续后置。
