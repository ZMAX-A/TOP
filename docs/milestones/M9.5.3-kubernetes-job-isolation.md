# M9.5.3 Kubernetes Job 执行隔离

## 目标

M9.5.2 已在本地单节点 Compose 中用 Docker Engine 提供每 Run 容器硬隔离，但父 Worker 必须持有 Docker Socket。
M9.5.3 新增 Kubernetes Job 执行器，把执行控制器与不受信任 Run Pod 分离：控制器只在专用 Namespace 内管理 Job、Pod、
ConfigMap、Secret 和 NetworkPolicy；Run Pod 使用独立 ServiceAccount 且禁用 Token 自动挂载，不获得控制面、数据库、
Redis、对象存储或 Kubernetes API 凭据。

## 每 Run 生命周期

控制器为每个不可变 Run Snapshot 创建唯一且带 Run ID 标签的以下资源：

- immutable ConfigMap：只读挂载 `snapshot.json`，超过 768 KiB 时失败关闭；
- immutable Secret：只包含 Snapshot 精确声明且 Worker 实际解析到的 `TESTOPS_SECRET_*`；
- Egress NetworkPolicy：`DENY_ALL`，或静态精确 CIDR allowlist 加集群 DNS；
- batch/v1 Job：`backoffLimit=0`、有界 active deadline 和完成后 TTL，Pod 内只有一个 Runner 容器。

Runner 完成后在内存 `/tmp` 写入退出标记并保持 Pod 存活，使可信控制器可通过受限 `pods/exec` 导出事件和有界 Run Tar。
控制器复用安全归档导入器，拒绝绝对路径、目录穿越、链接、设备文件、超量文件和超量归档，再校验 Run ID、Result
Schema 与隔离证据。成功、失败、取消和超时都会删除 Job、NetworkPolicy、Secret 和 ConfigMap；重试只回收名称和
`io.testops.run-id` 标签同时匹配的旧资源，任何同名非受管资源都失败关闭。

## Pod 硬隔离与运行态回读

Job 模板强制：

- `runAsNonRoot`，固定 UID/GID/FSGroup `1001`；
- `readOnlyRootFilesystem=true`、`allowPrivilegeEscalation=false`、`capabilities.drop=ALL`；
- Pod 与容器均使用 `RuntimeDefault` seccomp；
- `hostNetwork/hostPID/hostIPC=false`，无 hostPath、Docker Socket 或投影 ServiceAccount Token；
- Snapshot ConfigMap 只读，工作区和 `/tmp`、`/home/pwuser` 使用有界 emptyDir；
- CPU、内存和 ephemeral-storage 的 requests 与 limits 完全一致；
- OCI 镜像必须是 Snapshot 冻结的 `repository@sha256`。

Pod 进入 Running 后，控制器从 Kubernetes API 回读实际 Job、Pod 和 NetworkPolicy，校验 ServiceAccount、Token 自动挂载、
宿主命名空间、SecurityContext、Seccomp、卷、环境来源、requests/limits、NetworkPolicy selector/CIDR 以及容器状态中的
实际镜像摘要。只有全部一致时，失败或成功 Result 才能记录 `KUBERNETES` 硬隔离证据。

## 配置与调度

- `RUNNER_EXECUTION_MODE=KUBERNETES`；
- `RUNNER_KUBERNETES_NAMESPACE` 和非 `default` 的 `RUNNER_KUBERNETES_SERVICE_ACCOUNT`；
- `RUNNER_KUBERNETES_NETWORK_POLICY=DENY_ALL|ALLOWLIST`；
- `RUNNER_KUBERNETES_NETWORK_POLICY_ENFORCED=true` 是运维方对 CNI 确实执行 NetworkPolicy 的显式证明，缺少时 Worker
  拒绝启动；ALLOWLIST 还必须提供合法、去重并规范化的 `RUNNER_KUBERNETES_ALLOW_CIDRS`；
- CPU、内存、临时存储、执行超时和清理 TTL 均有上下界；
- 集群内默认使用短期投影 Token 的可信控制器，也支持显式 kubeconfig context 的集群外控制器。

控制面拒绝字段不完整、使用默认 ServiceAccount、自动挂载 Token 或缺少临时存储限额的 Kubernetes 心跳。相同 Pool
同时有 Subprocess、Docker Container 和 Kubernetes Worker 时，派发优先级为 Kubernetes > Container > Subprocess，
仍要求精确承载 Snapshot 中的自动化包仓库和摘要。

## 部署边界

[`infra/kubernetes/m9.5.3-runner.yaml`](../../infra/kubernetes/m9.5.3-runner.yaml) 提供 Namespace、Pod Security Admission
标签、控制器/Run 双 ServiceAccount、Namespace Role/RoleBinding、非敏感配置和控制器 Deployment 示例。控制器使用独立
短期投影 ServiceAccount Token；敏感控制面配置必须由外部创建的 `testops-worker-control-plane` Secret 注入。模板不包含
Docker Socket、ClusterRole、hostPath 或明文控制面凭据。

生产应用前必须替换示例 Registry、保存实际 OCI Manifest Digest，确认 CNI NetworkPolicy、Pod Security Admission、
Registry 拉取凭据、节点隔离和审计策略，并在隔离集群执行正常、失败、取消、超时、控制器重启和残留资源回收验收。

## 版本与验证边界

平台版本为 `0.29.0`，本阶段不改变数据库结构，Alembic Head 仍为 `20260820_0018`。本地测试覆盖配置门禁、最小 Secret、
Pod/Job/NetworkPolicy 构造、实际参数回读、镜像摘要、结果导出、安全导入、清理、Worker 路由、控制面心跳和调度优先级。
全量 Pytest 为 125 项通过、2 项因仓库外旧工作簿跳过，仓库标准入口 100 项通过；Ruff、Schema、不可变制品、Vue 严格
TypeScript 和 Vite 生产构建通过。独立 `testops-m953-verify` Docker Compose 栈完成 0.29.0 普通及中断恢复 Smoke，证明
新增契约和 Worker 依赖没有破坏现有容器主业务链路；该结果不属于 Kubernetes 验收。

本机没有 `kubectl` 或可用 Kubernetes Context，因此未执行真实 API Server、CNI、RBAC、调度器、容器运行时、Pod
Security Admission 及集群异常恢复验收。发布前必须在隔离集群补齐这些证据，不能用 Mock、清单检查或 Docker Smoke
替代。
