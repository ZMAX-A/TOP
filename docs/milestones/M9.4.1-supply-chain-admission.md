# M9.4.1 签名、来源证明与 SBOM 准入

> 本文记录 `0.25.0` 时的初始信任边界；`0.26.0` 已由
> [M9.4.2](M9.4.2-signed-verifier-envelopes.md) 将 System Admin 代提交升级为专用验证器服务身份和防重放签名
> Envelope。

## 目标

M9.2 只能证明 Worker 预装了与 Run Snapshot 完全相同的 `repository@sha256`，不能证明该摘要来自受信任的构建
流水线，也不能证明签名、构建来源和软件物料清单已经通过策略。M9.4.1 在自动化包执行前增加供应链准入，并把实际
采用的证明记录冻结进 Run Snapshot。

## 信任边界

- Cosign、SLSA provenance 和 SBOM 的原始验证在受控 CI/供应链验证器执行；控制面不持有 Registry 凭据、签名
  私钥，不下载远端镜像或证明，也不执行来自 API 的命令；
- Sigstore Cosign 验证必须对精确 `repository@digest` 执行，并设置批准的 certificate identity 和 OIDC issuer；
  Cosign 默认校验签名载荷内的镜像摘要与目标镜像一致；
- provenance 必须是验证器支持的 SLSA/in-toto 证明，校验 subject 摘要、`buildDefinition`、`runDetails.builder.id`
  和源码修订；SBOM 必须由发布策略认可的 CycloneDX/SPDX 校验器检查结构、组件与漏洞门禁；
- 验证器只把结果和原始证据的 SHA-256 摘要提交给控制面，原始 Sigstore bundle、provenance、SBOM 和扫描报告继续
  由 CI 制品库不可变保留。控制面当前依赖 System Admin 会话代表可信验证器提交报告，尚未提供独立服务身份或报告
  二次签名；这是后续强化边界，不得把项目管理员手工勾选当作供应链验证。

参考规范：

- [Sigstore Cosign 验证](https://docs.sigstore.dev/cosign/verifying/verify/)；
- [SLSA Build Provenance](https://slsa.dev/spec/v1.2-rc2/build-provenance)；
- [CycloneDX 1.7 JSON](https://cyclonedx.org/docs/1.7/json/)。

## 数据与准入策略

- 新增追加式 `automation_package_supply_chain_verifications`，保存 VERIFIED/REJECTED、当前策略版本、验证器、镜像
  摘要、Sigstore bundle/provenance/SBOM 摘要、四项检查结果、证书颁发者/身份、builder、源码仓库/修订、原因、
  操作人和确定性报告摘要；同一包的同一报告幂等返回，不覆盖历史；
- `automation_packages` 新增 `supply_chain_status`、当前验证记录 ID 和判定时间。新 DRAFT 从 `PENDING` 开始；已有
  包迁移为 `LEGACY`，已有 DRAFT 迁移为 `PENDING`；
- VERIFIED 报告要求签名、透明日志、provenance 和 SBOM 四项全部为 true，镜像摘要必须等于包摘要，策略版本必须
  等于平台当前版本；
- VERIFIED 还必须逐项精确命中环境允许清单：验证器、证书颁发者、证书身份、builder ID、源码仓库。任一允许清单
  为空时失败关闭；REJECTED 报告必须有原因，并允许作为失败证据写入；
- 最新报告更新包级准入状态，但不修改历史记录。重复提交旧报告只返回原记录，不会把包从更新的判定回滚到旧状态。

## API 与权限

- `GET .../automation-packages/{package_id}/supply-chain-verifications`：项目读权限可查看完整判定历史；
- `POST .../automation-packages/{package_id}/supply-chain-verifications`：仅 System Admin 可提交可信 CI 报告；Project
  Admin 仍可管理包生命周期，但不能自行宣称签名或来源证明通过；
- 工作台展示包级 `LEGACY/PENDING/VERIFIED/REJECTED`、策略版本、报告摘要、验证器、builder、判定原因和历史；
  PENDING/REJECTED 草稿的验证和激活按钮不可用，服务端仍是最终安全边界。

## 执行边界

- PENDING/REJECTED 包不能创建验证 Run、普通 Run、定时回归计划或计划触发，也不能从历史 Run 重跑；
- ACTIVE 包收到新的 REJECTED 报告后立即阻止新执行、计划触发和重跑，但不会改写 Snapshot、自动篡改生命周期状态
  或强杀已经在途的 Run；安全事件仍应由管理员填写原因执行吊销；
- VERIFIED 包创建 Run 时将验证记录 ID、报告摘要、策略版本、验证器、三类证据摘要、证书身份、builder、源码仓库
  和修订冻结进 `automation_package.supply_chain`；Worker 继续只按 M9.2 的运行时三元组准入，不需要 Registry 凭据；
- LEGACY 包保持现有执行和重跑兼容，但页面明确标记缺少新证明。生产迁移完成后应通过后续策略去除 LEGACY 豁免。

## CI 操作顺序

1. 构建并推送新镜像，取得最终 OCI Manifest Digest；
2. 创建 DRAFT 自动化包，包摘要必须使用该 Manifest Digest；
3. 可信验证器对精确摘要执行 Cosign 签名/透明日志验证，校验证书 issuer/identity；
4. 验证 SLSA/in-toto provenance 的 subject、builder、源码仓库与修订，再验证 SBOM 结构及漏洞门禁；
5. 对 Sigstore bundle、provenance 和 SBOM 原始制品计算 SHA-256，把结果通过 System Admin 身份提交到供应链验证
   API；允许清单不匹配时修正流水线或策略，禁止伪造布尔结果；
6. 工作台显示 VERIFIED 后，再部署承载新摘要的 Worker、创建全量验证 Run、激活并切换业务流量；
7. 后续扫描或证明复核失败时提交 REJECTED，立即停止新执行并进入吊销处置。

## 兼容、版本与验证

- 平台版本提升到 `0.25.0`，Alembic Head 为 `20260820_0017`；迁移支持 upgrade/downgrade，降级会删除供应链
  判定记录与包级准入字段；
- Run Snapshot 的供应链引用是可选字段，历史 `1.0` Snapshot、旧 Runner 和 LEGACY 包继续可解析；
- 集成测试覆盖 PENDING/REJECTED 关闭、摘要和身份不匹配、VERIFIED 与报告幂等、历史倒序、Snapshot 冻结、激活、
  ACTIVE 后重新拒绝、新执行/计划/重跑阻断、System Admin 权限及审计动作；
- 单元测试覆盖 VERIFIED 四项检查、REJECTED 原因和环境允许清单解析；Schema、迁移图、发布元数据和前端严格类型
  检查纳入发布验证。

本机增量预验收结果：全量 Pytest `103 passed`，仓库标准入口 `78 tests OK`；Ruff 检查通过且 `149 files`
格式一致；Schema 导出检查、不可变基线/Runner 制品摘要检查、发布/部署契约测试均通过；Vue 严格 TypeScript 检查
和 `0.25.0` Vite 生产构建通过。Alembic 唯一 Head 为 `20260820_0017`，全量离线升级和
`20260820_0017 -> 20260820_0016` 离线降级 SQL 生成通过。本机没有 Docker CLI，因此尚未执行真实 PostgreSQL
升级/降级/再升级往返、Compose 全栈 Smoke，也没有用真实 Cosign/SLSA/SBOM 制品执行 CI 验证；这些仍是生产门禁，
不能由控制面测试替代。

## 后续

M9.4.1 不负责远端 Registry 拉取，也不把 Docker Socket 暴露给 Worker。后续优先增加供应链验证器专用服务身份和
签名报告 envelope，再建设 Registry 凭据隔离、每个 Run 独立容器/Pod、只读根文件系统、资源限制和网络策略。
