# M7.1：项目执行配额

## 目标与完成范围

M7.1 为进入规模化执行建立第一道项目级准入边界，避免单个项目无限创建 Run 挤占
控制面、队列和 Runner 容量。本阶段完成：

- 每个项目配置最大在途 Run 数和 UTC 自然日最大创建量，默认分别为 20 和 500；
- 在途口径固定为 `QUEUED + PREPARING + RUNNING`，终态 Run 和已取消的排队 Run
  不占用在途名额；
- 普通执行、用例变更验证、候选全回归和重跑统一经过同一准入检查；
- 幂等重放先返回原 Run，不重复消耗配额；被配额拒绝的请求不创建 Run、Run Case、
  事件、Outbox 或审计中的成功创建记录；
- Project Admin 与 System Admin 可修改配额，项目成员可读取实时用量；修改操作写入审计；
- 项目设置页新增“执行配额”标签，展示排队/准备/执行拆分、今日创建量、剩余容量、
  80% 预警和阻断状态。

## 并发与一致性边界

创建 Run 前，控制面使用 `SELECT ... FOR UPDATE` 锁定所属项目行，再读取当前用量并在
同一事务中创建不可变 Snapshot、Run Case、事件和 Outbox。PostgreSQL 下同一项目的
并发创建会串行经过准入点，不能通过“同时读到旧计数”绕过上限；不同项目互不阻塞。

配额只负责控制进入调度链的 Run 数量，不等价于 Runner 进程并发或资源池隔离。已经
在途的 Run 不会因为管理员把上限调低而被自动取消；新请求会暂停准入，直到用量回落。

## 数据库与 API

- Alembic `20260813_0005` 为 `projects` 增加 `max_in_flight_runs` 和
  `max_daily_runs`，并建立数据库范围约束；
- `GET /api/v1/projects/{project_id}/execution-policy` 返回配置、实时用量、剩余容量、
  UTC 日窗口和 `AVAILABLE`、`NEAR_LIMIT`、`BLOCKED` 状态；
- `PATCH /api/v1/projects/{project_id}/execution-policy` 增量更新配额；
- 最大在途数范围为 1–500，每日创建量范围为 1–100000，空对象和显式 `null` 均拒绝。
